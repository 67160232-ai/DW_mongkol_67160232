## 1 OLTP

### โค้ด/ผลรันสองรอบ/คำอธิบายสถานะและ ETL

กิจกรรมนี้ใช้ฐานข้อมูล `oltp.db` ซึ่งมีตาราง `orders` และมีข้อมูลเริ่มต้นของออเดอร์ `O1004` เป็นสถานะ `PENDING` โดยโจทย์กำหนดให้เปลี่ยนสถานะจาก `PENDING` เป็น `PAID` และต้องใช้ `WHERE` ตรวจทั้ง `order_id` และ `status`

**โค้ดที่ใช้**

```python
with sqlite3.connect(p) as con:
    print('Before:', con.execute('SELECT * FROM orders').fetchall())

    cur = con.execute("""
        UPDATE orders
        SET status = 'PAID'
        WHERE order_id = 'O1004'
          AND status = 'PENDING'
    """)
    print('rowcount:', cur.rowcount)

    print('After:', con.execute('SELECT * FROM orders').fetchall())
```

### ผลการรันรอบที่ 1

```text
Before: [('O1004', 'PENDING')]
rowcount: 1
After: [('O1004', 'PAID')]
```

### ผลการรันรอบที่ 2

```text
Before: [('O1004', 'PAID')]
rowcount: 0
After: [('O1004', 'PAID')]
```

รอบแรกแก้ไขข้อมูลจำนวน **1 แถว** เพราะสถานะเดิมของ `O1004` เป็น `PENDING` จึงตรงกับเงื่อนไขใน `WHERE`

รอบที่สองแก้ไข **0 แถว** เพราะสถานะถูกเปลี่ยนเป็น `PAID` แล้ว ทำให้ไม่ตรงกับเงื่อนไข `status = 'PENDING'`

การกำหนดเงื่อนไข `status` มีความสำคัญ เพราะช่วยป้องกันการเปลี่ยนสถานะซ้ำหรือเปลี่ยนข้อมูลที่ไม่อยู่ในสถานะที่คาดไว้ ทำให้การ UPDATE มีความปลอดภัยมากขึ้น

กิจกรรมนี้เป็น **OLTP** เพราะเป็นการทำงานกับรายการธุรกรรมและมีการเปลี่ยนแปลงข้อมูลสถานะของออเดอร์โดยตรง แม้ว่าจะมี `SELECT` สำหรับอ่านข้อมูล แต่การดำเนินการหลักคือการ UPDATE สถานะของธุรกรรม ซึ่งเป็นลักษณะของ OLTP

การเปลี่ยนข้อมูลใน `oltp.db` **ไม่ทำให้ยอดใน `warehouse.db` เปลี่ยนทันที** เพราะฐานข้อมูลทั้งสองแยกจากกัน และใบแลประบุว่า `oltp.db` เป็นกิจกรรมสถานะที่แยกจากคลังข้อมูลและไม่ได้ทำ ETL อัตโนมัติ

ในระบบจริงควรมี **ETL/ELT หรือกระบวนการ Data Pipeline** สำหรับดึงข้อมูลจากระบบธุรกรรม นำมาแปลงและตรวจสอบ แล้วโหลดเข้าสู่ Data Warehouse

# 2 Grain และ Star Schema

## 2.1 Star Schema

โครงสร้างของระบบเป็น **Star Schema** โดยมี `fact_sales` เป็น Fact Table อยู่ตรงกลาง และเชื่อมกับ Dimension 3 ตาราง ได้แก่ `dim_date`, `dim_product` และ `dim_store`

```text
                       dim_date
                    PK: date_key
                         │
                         │ 1:N
                         ▼
dim_product ───────► fact_sales ◄─────── dim_store
PK: product_key       PK: order_id       PK: store_key
                      PK: line_no
                      FK: date_key
                      FK: product_key
                      FK: store_key
                      quantity
                      unit_price
```

### Primary Key / Foreign Key

**fact_sales**
- PK = `(order_id, line_no)`
- FK = `date_key`
- FK = `product_key`
- FK = `store_key`

**dim_date**
- PK = `date_key`

**dim_product**
- PK = `product_key`

**dim_store**
- PK = `store_key`

### Grain

Grain ของ `fact_sales` คือ

> **1 แถว หมายถึงสินค้า 1 รายการใน 1 ออเดอร์ หรือ 1 order line**

ตัวอย่าง `O1001` มี 2 แถว เพราะมีสินค้าจำนวน 2 รายการในออเดอร์เดียวกัน ได้แก่ Tea และ Cookie

ดังนั้นจึงไม่ควรนับจำนวนแถวเป็นจำนวนออเดอร์โดยตรง เพราะ 1 ออเดอร์สามารถมีหลายรายการสินค้าได้

## ทดลองลบ aggfunc

หากลบ `aggfunc='sum'` ออกจาก Pivot ค่าเริ่มต้นของ pandas จะเป็นค่าเฉลี่ย (`mean`) สำหรับข้อมูลที่มีหลายรายการในกลุ่มเดียวกัน

ตัวอย่าง Bangkok เดือนกันยายนมีรายการ:

```text
300
240
```

ดังนั้น

```text
mean = (300 + 240) / 2
     = 270
```

ดังนั้นค่า **270 บาทไม่ได้หมายถึงยอดขาย** แต่หมายถึง **ค่าเฉลี่ยยอดขายต่อรายการขาย (line)** ของ Bangkok ในเดือนกันยายน

การแก้ไขคือกำหนด

```python
aggfunc='sum'
```

เพื่อให้ Pivot แสดงยอดขายรวมตามโจทย์

## q09 — UNION ALL

ใช้ `UNION ALL` เพื่อแสดงยอดขายรายเดือนและแถว `ALL`

ผลรวมรายเดือน:

| Month | Revenue |
|---|---:|
| 2026-08 | 490 |
| 2026-09 | 900 |
| ALL | 1,390 |

ต้องระวังว่า `UNION ALL` จะเก็บทุกแถวเอาไว้ ดังนั้นหากนำแถวรายเดือนและแถว `ALL` มาบวกทั้งหมดอีกครั้ง จะทำให้เกิด **Double Counting**

ตัวอย่าง:

```text
490 + 900 + 1390 = 2780
```

ซึ่งไม่ใช่ยอดขายจริง ยอดขายจริงคือ **1,390 บาท**

## q10 — Revenue, Orders, AOV และ AVG(amount)

ผลลัพธ์:

```text
Revenue = 1,390 บาท
Orders  = 6
AOV     = 231.67 บาท
AVG     = 173.75 บาท
```

### การคำนวณ AOV

สูตร:

```text
AOV = SUM(amount) / COUNT(DISTINCT order_id)

    = 1,390 / 6

    = 231.67 บาทต่อออเดอร์
```

AOV จึงมีหน่วยเป็น **บาทต่อออเดอร์**

ส่วน

```text
AVG(amount) = 1,390 / 8
            = 173.75 บาทต่อรายการสินค้าใน fact
```

จึงไม่เท่ากับ AOV เพราะตัวหารต่างกัน

- **AOV** → หารด้วยจำนวนออเดอร์
- **AVG(amount)** → หารด้วยจำนวนรายการขาย (lines)

ใบแลประบุให้ใช้ `COUNT(DISTINCT order_id)` ในการคำนวณ AOV และให้ทำการหารแบบทศนิยมใน SQLite

## ประเภท Measure

### 1. Additive

**Revenue / amount**

สามารถนำมาบวกได้ทุกมิติ เช่น

```text
ยอดขายเดือนสิงหาคม + ยอดขายเดือนกันยายน
```

จึงเป็น Additive Measure

### 2. Semi-additive

**Stock / สต็อกสิ้นวัน**

สามารถรวมได้ในบางมิติ เช่น รวมข้ามสินค้า แต่ไม่ควรนำสต็อกของแต่ละวันมาบวกกันเพื่อหาสต็อกของเดือน เพราะจะเกิดความหมายที่ไม่ถูกต้อง

ควรใช้ค่าปลายงวด เช่น End-of-day หรือ Last value ตามบริบท

### 3. Non-additive

**AOV**

ไม่ควรนำ AOV ของแต่ละเดือนมาบวกกัน เช่น

```text
AOV เดือน 1 + AOV เดือน 2
```

จะไม่มีความหมายเป็น AOV ของทั้งช่วง

ควรคำนวณใหม่จาก

```text
SUM(amount) / COUNT(DISTINCT order_id)
```

โดยใช้ตัวหารที่ถูกต้องของช่วงเวลานั้น

มีการใช้ AI เพื่อช่วยทำความเข้าใจแนวคิด OLTP, OLAP, Grain, Star Schema, Roll-up, Drill-down, Slice, Dice, Pivot และช่วยตรวจสอบแนวทางการเขียน SQL/Python

หลังจากนั้นมีการตรวจสอบผลลัพธ์กับข้อมูลใน `warehouse.db` และผลที่ได้จากการรันจริงด้วยตนเอง โดยเฉพาะยอดรวม **1,390 บาท**, จำนวน **8 lines**, **6 orders** และการคำนวณ AOV เพื่อให้แน่ใจว่าตรงกับ Grain ของข้อมูล
